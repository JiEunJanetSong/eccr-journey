01 · A reproducible system, with three separate outputs

ECCR connects a teacher’s reading plan, editable book production, and a static listening app. Reproduction starts by naming the exact edition and deciding which output you are building.

Components

  • Authoring materials: manuscripts, approved images, fonts, recordings, scripts and page maps. Keep these so the outputs can be rebuilt.
  • Print resources: Books 1–9, Book 0, parallel Readers A–C, book-specific assessments, entry baselines and Writing Book. These are separate products with different learning purposes.
  • Listening software: two interfaces share one metadata source—picturebook/ for tapping printed text, audio/ for a list and sequential playback. The journey archive is a third, documentation website.

Procedure

  • Write a target list: named PDF edition, target pages, language, recordings, supported screens and offline requirement.
  • Create a source manifest before changing anything; record file paths, page counts and hashes. Treat newly generated materials as candidates until reviewed.

Verification

  • A PDF being final does not establish that the deployed listening app uses that PDF. Verify both independently.
The inspected public application snapshot (3b87245) contains Books 1–7 and older bilingual text. The print folder also contains revised Books 1–9 and later supplementary materials. Reproducing the current app and integrating the latest PDFs are different tasks.

02 · Turn conversation into an inspectable brief

A useful brief separates what the teacher supplied, what the AI proposed, and what the teacher later corrected. Dates alone do not resolve conflicting editions.

Components

  • Store learner text separately from translation notes. Yaw’s English glosses helped Janet understand Twi; the later decision removed them from the learner editions of Books 4–6.
  • A page record should identify source message, book, physical PDF page, printed page label, exact text, illustration requirement and approval status.
  • Use the latest explicit content decision and verified target file. Preserve original messages verbatim and label summaries or translated explanations as editorial.

Procedure

  • For each request, write an acceptance check before asking AI to generate: for example, exactly two goats and two children, or one illustration with connected sentences.
  • When feedback arrives, record old text → approved text → affected outputs. Include assessments and audio mapping in the impact list.

Verification

  • The text “four letters” constrains word length; it does not mean four words in each sentence, and it does not by itself establish decodability.

03 · Keep the words editable and the pictures separate

The early Book 2 source uses XeLaTeX: images sit above typeset Twi text. Later builders use ReportLab for precise PDF layout. The common principle is to keep text out of generated pictures.

Components

  • Save each accepted image, scene prompt and source reference. For repeated characters, preserve identity, clothing, relative height and scene continuity.
  • Use image generation to supply or change visual content. Use layout code for centering, margins, page numbers and text corrections.
  • Dependencies differ by route: XeLaTeX plus fontspec for the early TeX source; Python, ReportLab, PyMuPDF, Pillow and sometimes pypdf for later PDF builders. Font files are explicit inputs.

Procedure

  • Approve a small text-and-image sample first. Then expand the same rules across the book.
  • Render the PDF and extract its text. Inspect Twi characters such as ɔ, ɛ and Ɔ, text size, missing body parts, image overlap and real writing space.

Verification

  • For identical visual output, reuse the approved images. Repeating an image prompt is not a deterministic rebuild of the same artwork.
  • The historical TeX and Python scripts include machine-specific font paths. Resolve those paths before rebuilding on another computer.
The archived early book2.tex builds an earlier A5-era manuscript, not the present 20-page A4 Book 2. It demonstrates the method; it is not a one-command rebuild of every subsequent revision.
pdfinfo book.pdf
pdffonts book.pdf
pdftotext -layout book.pdf -
pdftoppm -png -r 120 book.pdf /tmp/eccr-page

04 · Manage print and app editions with page maps

The same book can produce several valid editions. Removing blank pages changes indexes even when every retained picture is unchanged.

Components

  • The September 15 app derivative removes 15 filler pages across Books 1–9 and records original_pdf_page → app_pdf_page. It was prepared as PDFs and explicitly not uploaded at that time.
  • Print derivatives preserve facing-page and binding requirements. Printed folios, physical PDF pages and screen indexes are three distinct identifiers.
  • Final main-book folio correction moves even numbers left and odd numbers right. Earlier binding subfolders contain different experiments; do not apply one folder’s README to all editions.

Procedure

  • Select the source edition, preserve it, and build into a new output location. Save a mapping row for every retained page.
  • Apply that map to image filenames and audio items. Remeasure hotspots whenever layout changes.

Verification

  • Compare retained pages against the source by rendering or pixel comparison. Check blank pages, cover order, margins, numbered-page side and page count.

05 · Generate assessments and parallel readers from explicit rules

Reusing a visual style is not enough. Each material needs its own learning purpose and verification rules.

Components

  • Book-specific assessments follow the content taught in that book. Entry baselines ask about sounds before instruction and keep learner and teacher item order aligned.
  • Readers A–C each contain 12 texts in 40 pages and share a planned scope. Their source manuscripts.json defines sentences, blend words, questions, target vowel and scene.
  • The builder audits cumulative vowels, word length, VC/CVC constraints, sentence counts, distinct passages, PDF page count, folio side and one main image per story page.
  • The combined Book 0 is 90 pages, preserving the earlier 80-page book as Book 0-pre. Writing-line sets use 2.5 mm between lines: four lines span 7.5 mm.

Procedure

  • Put manuscript decisions into structured records before laying out pages. Generate a teacher key from the same records.
  • Run vocabulary and layout checks, then ask Yaw to review sound values, teaching order, meanings and learner readiness.

Verification

  • A–C are practice books within a shared planned scope, not validated equivalent tests. Four-letter word length and automated spelling checks do not validate pronunciation or classroom effectiveness.
The full builders depend on archived assets and locally configured fonts; a clean-room tutorial must first supply those inputs or create replacements. There is no single universal build command for all final PDFs.

06 · Map every recording to the exact printed unit

Teacher audio becomes a deployment asset. A transcript field is a label, not proof that the recording says the same thing.

Components

  • Keep original recordings, split them into tappable words, sentences or headings, and record the clip path and language beside the exact printed text.
  • Use automated transcription for draft timestamps only. Listen for Twi accuracy, clipped first/last sounds, missing pauses and narration not printed on the page.
  • For genuinely bilingual learner pages, use separate language-specific clips. For the revised Twi-only Books 4–6, retire English playback rather than preserving obsolete glosses.
  • recordingMissing prevents synthesized fallback. GitHub Pages uses packaged MP3s and an empty TTS API base; the teacher’s Mac need not be running.

Procedure

  • Create a text → source recording → start/end → exported clip table. Approve clips by listening before registering them.
  • When wording changes, compare the actual clip before rerecording. A spelling correction alone may not change the sound.

Verification

  • Play the beginning, middle and end of each clip, then test rapid switching. Check that repetition gaps are present and playbackRate is 1.

07 · One data contract connects paper, picture and sound

window.ECCR_A4_BOOKS supplies both listening interfaces. Each book contains pages; each page contains its image and audio items.

Components

  • Book: unique id, title, assetDir, pages. Page: title, image, audio. Audio item: text, speechText, audioSrc or recordingMissing, lang, box or boxes.
  • Hotspots are transparent buttons over the page image. x, y, w and h are percentages of the full image; using pixels without conversion breaks alignment when the page scales.
  • picturebook/ resolves audioSrc directly; audio/ prefixes ../picturebook/. Keep those path rules distinct while sharing the same records.

Procedure

  • Render the approved PDF into sequential JPEGs. Measure a generous but non-overlapping text rectangle, then convert its pixels to percentages.
  • Register the image, visible text and matching clip together. Test a single page before scaling to the full library.

Verification

  • Check every referenced file exists and every region stays inside 0–100%. Visually confirm phone and desktop alignment; valid coordinates alone do not prove correct placement.
{
  text: "Sam has a cap.",
  speechText: "Sam has a cap.",
  audioSrc: "audio/book7/page-04-01.mp3",
  box: { x: 47, y: 28, w: 36, h: 8 },
  lang: "en"
}

// x = leftPixel / imageWidth * 100
// y = topPixel / imageHeight * 100
// w = boxWidth / imageWidth * 100
// h = boxHeight / imageHeight * 100

08 · Small runtime, explicit playback state

The app uses HTML, CSS and plain JavaScript with an HTML audio element. There is no required frontend framework, database, login or server runtime.

Components

  • Changing a book or page stops the current recording. Tapping another sentence invalidates the previous playback before starting the next.
  • playbackToken distinguishes current events from delayed ended/error events. Audio Practice also uses sequenceToken to cancel an old Play page sequence.
  • Responsive CSS changes control placement and page width for mobile. The reader image and its hotspot layer must always scale together.

Procedure

  • Implement select book → render page → render hotspots → play item, then handle cancellation and missing audio explicitly.
  • Reuse the same content contract in the list interface instead of copying the manuscripts into another independent dataset.

Verification

  • Tap A then B rapidly; change page mid-playback; play a whole page then switch books; select missing audio. No stale highlight or previous sound should remain.

09 · Offline readiness is a complete download plus a fresh restart

A page visible while online is not proof of offline use. The complete images-and-audio package must be cached and remain usable after the app is closed.

Components

  • manifest.webmanifest describes installation. pwa.js registers the service worker and shows progress. offline-assets.js lists required files. sw.js saves, updates and serves them.
  • Save offline sends CACHE_ALL_OFFLINE_ASSETS; progress messages count files; Offline ready is reported only after the package is present.
  • Browsers may request part of an MP3. createRangeResponse returns a 206 response with the requested cached byte range so offline audio can play.

Procedure

  • After changing content, regenerate the asset list, use a new cache name, and update asset query versions. Do not hand-edit the generated list.
  • Download online until Offline ready. Fully close the app, disconnect the network, reopen it in the same browser/profile and test both images and audio.

Verification

  • Repeat on a phone and desktop. A successful warm session does not replace a cold offline restart. Browser storage can be cleared or evicted.
npm run build:offline
npm run check
npm run serve
# Open http://localhost:4173/

10 · Release with evidence, and preserve the next maintainer’s starting point

A repeatable release links approved inputs to outputs, verifies the actual deployed files, and explains what still needs teacher review.

Components

  • The inspected package.json check script runs node --check on six JavaScript files. It checks syntax only; it does not validate references, learning content, hotspot positions or audio.
  • The application’s GitHub workflow uploads the repository as a static Pages artifact on main pushes. Keep development-only material and private source records outside the published package.
  • The release record should name the source edition, page/audio inventory, cache version, changed files, automated checks, device checks and open questions.

Procedure

  • Check syntax and file references, render the PDFs, listen to clips, verify mobile interaction and perform a cold offline restart. These checks answer different questions.
  • After deployment completes, open the published URL and confirm the new revision and resource paths. Compare live metadata with the approved source before claiming synchronization.
  • Save a concise handoff with the next safe operation. Include the source files and approved assets needed to rebuild; prompts alone are not a complete source package.

Verification

  • Separate “the assistant reported completion,” “a local file was inspected,” and “the deployed app was verified.” Each supports a different claim.
